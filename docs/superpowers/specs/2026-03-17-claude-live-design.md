# claude-live — Design Spec

**Date:** 2026-03-17
**Status:** Approved

## Overview

`claude-live` is a portable, locally-run npm package that visualizes Claude Code activity in realtime using an animated PixiJS canvas. Any developer can spin it up with `npx claude-live`, add a copy-paste hook config to their Claude Code settings, and immediately see a living force-directed graph of what Claude is doing.

---

## Goals

- Zero-friction setup: `npx claude-live` + copy-paste hook config
- Realtime: sub-second latency from Claude action to canvas update
- Visual: animated PixiJS canvas, not a dashboard or log viewer
- Local-only: no cloud, no auth, no persistence
- Multi-session aware: multiple Claude Code sessions visible simultaneously

---

## Architecture

```
Claude Code (settings.json hooks)
  └─ shell: echo "$CLAUDE_HOOK_DATA" | curl -s -X POST localhost:3141/hook \
            -H "Content-Type: application/json" -d @- || true

SSE Server  (server/index.js, port 3141)
  ├─ POST /hook     — receives all hook events, fans out to SSE clients
  └─ GET  /events   — SSE stream (text/event-stream)
  └─ GET  /         — serves static Vite build

Browser
  └─ EventSource('/events') → normalizes events → PixiJS canvas
```

The `|| true` on the hook command ensures Claude Code never blocks or errors if the server is not running. Hook failures are silent and non-blocking by design.

The server serves the pre-built static Vite bundle from `client/dist/`. In dev mode, `npm run dev` starts the server + `vite dev` concurrently, with Vite proxying `/events` to `:3141`. The published npm package ships the pre-built client — no Vite required at runtime.

---

## Hook Integration

All four Claude Code hook types are captured: `PreToolUse`, `PostToolUse`, `Stop`, `Notification`.

**Raw Claude Code payload** (from `$CLAUDE_HOOK_DATA`):
```json
{
  "hook_event_name": "PreToolUse",
  "tool_name": "Read",
  "tool_input": { "file_path": "/src/foo.ts" },
  "session_id": "abc123"
}
```

`session_id` is provided by Claude Code in the hook environment. If absent or empty (e.g. older Claude Code versions), the server assigns a fallback: `"unknown-<sha1(remote_ip+timestamp)[:8]>"`. `PostToolUse` additionally includes `tool_response`. `Stop` and `Notification` have no `tool_input` or `tool_response`.

**Server-normalized event shape:**
```ts
{
  id: string,              // uuid generated by server
  session_id: string,      // from payload
  timestamp: number,       // Date.now() at receipt
  hook_event_name: string, // PreToolUse | PostToolUse | Stop | Notification
  tool_name: string | null,
  tool_input: object | null,
  tool_response: object | null  // JSON object on PostToolUse, JSON null otherwise (never omitted)
}
```

## Data Model (Client)

### Rolling Event Buffer

- Stores the last **100 events** in an ordered array, oldest first
- When a new event arrives, it is appended; if length exceeds 100 the oldest is removed
- No persistence — buffer resets on page reload

### Node Age

Age is measured in **event count units** (not time). A node's age = distance from the most recent event in the buffer that references this node (0 = just touched, 99 = last referenced 99 events ago). Age is recalculated each frame by scanning the buffer.

- When a node receives a new event, its age resets to 0 automatically
- When the oldest event referencing a node is pushed out of the 100-event buffer, the node's age becomes 100 on the next frame — it begins fading immediately and is removed one frame later
- Visual mappings (all linear, 0 = youngest, 100 = oldest):
  - Opacity: `1.0 → 0.0`
  - Node radius: `100% → 40%` of base size
  - Edge opacity: `0.7 → 0.0`
- Nodes at age ≥ 100 are removed from the scene at the start of the next frame. Removed nodes are also removed from the force simulation immediately.

### Session Map

```ts
Map<session_id, {
  nodes: Map<nodeKey, Node>,
  clusterCenter: { x: number, y: number },  // target position in canvas space
  label: string  // session_id (truncated)
}>
```

### Node Identity

Nodes represent the **target of a tool action**, not the tool itself. Node key and type depend on the tool:

| Tool | Node key | Node label |
|------|----------|------------|
| Read, Edit, Write, Glob, Grep | `file:<file_path>` | filename (basename) |
| Bash | `bash:<sha1(command)>` | `$ <command[:20]>` |
| WebFetch | `web:<hostname>` | hostname |
| Stop | `session:stop` | `✓ done` |
| Notification | `notification:<message[:20]>` | `💬 <message[:20]>` |
| Other / unknown | `tool:<tool_name>` | tool name |

File nodes are larger (base r=12). All other nodes are smaller (base r=7).

Edges connect the event's source node to the file/target node when both exist. For non-file tools (Bash, WebFetch) there is no edge — the node floats freely within its cluster.

## PixiJS Canvas

### Color by Tool Type

| Tool | Color |
|------|-------|
| Read | `#4ade80` green |
| Edit / Write | `#60a5fa` blue |
| Bash | `#f59e0b` amber |
| Grep / Glob | `#a78bfa` purple |
| WebFetch | `#f472b6` pink |
| Stop | `#888888` gray |
| Notification | `#34d399` teal |
| Other | `#555555` |

### Nodes

- Circle with glow halo (radial gradient, radius = node.r * 2.5)
- Label rendered below node, font-size 11px, opacity matches node opacity
- On new event: ripple animation — a ring expands from node center outward (300 simulation units over 600ms), color = tool type, fades as it expands. All distance constants in this spec are in simulation units (1:1 with CSS pixels at default canvas scale).

### Edges

- Straight line between connected nodes, color = tool type, opacity = edge age mapping
- Only drawn within the same session cluster

### Force Simulation

Runs every frame (requestAnimationFrame) using a simple Euler integrator:

**Forces applied each tick:**

1. **Node–node repulsion** (within cluster): `F = k / dist²`, applied to all pairs closer than 150px. `k = 800`.
2. **Edge attraction**: nodes connected by an active edge attract each other toward `targetDist = 80px`. `F = (dist - targetDist) * 0.03`.
3. **Cluster center gravity**: each node is pulled toward its cluster's `clusterCenter` (the cluster's assigned stable canvas position, not center of mass). `F = (clusterCenter - node.pos) * 0.005`.
4. **Cluster–cluster repulsion**: cluster centers repel each other. `F = 2000 / dist²`, minimum separation 250px.
5. **Canvas boundary**: soft repulsion from edges, kicks in within 60px of canvas edge.

**Integration:** `velocity += force; velocity *= 0.88 (damping); position += velocity`

Simulation runs continuously (always animating). Nodes that are being removed (age=100) continue in the simulation until their opacity reaches 0, then are destroyed.

### Multi-Session Clusters

- Each new `session_id` spawns a cluster at a random canvas edge position
- Clusters drift to their stable positions via cluster-center gravity + inter-cluster repulsion
- On `Stop` event: all nodes in the cluster have their age set to 80 immediately (so they fade out over the next ~20 event-age units), then the cluster object is removed once all its nodes reach age 100
- Clusters display a small label (truncated session_id) at their assigned `clusterCenter` position
- Maximum 6 simultaneous clusters. When a 7th arrives, the oldest cluster is evicted immediately (its Stop fade, if in progress, is cancelled and nodes are destroyed synchronously)

## SSE Behavior

- Server sends a `heartbeat` event every 15 seconds to keep connections alive through proxies
- On reconnect (`EventSource` auto-reconnects): client receives events from the point of reconnection only — no replay (buffer is in-memory, not replayed over SSE)
- Multiple browser tabs all receive the same stream independently (each GET /events is its own SSE connection)
- Server buffers the last **100 events** (same as client rolling buffer) and sends them as individual SSE messages immediately on new connection (so a freshly opened tab isn't empty)

## CLI / Distribution

```bash
npx claude-live            # starts server on :3141, opens browser
npx claude-live --port 4000  # custom port
```

`bin/claude-live.js`:
1. Tries to bind the port; if in use, auto-selects the next available port and prints it
2. Starts `server/index.js` serving the pre-built static client from `client/dist/`
3. Opens `http://localhost:<port>` in the default browser

**Build:** `npm run build` runs `vite build` in `client/`, outputs to `client/dist/`. The `prepublishOnly` script runs the build so `client/dist/` is always included in the published package. `vite` is a `devDependency` — not required at runtime.

**Dev mode:** `npm run dev` uses `concurrently` to run `node server/index.js` + `vite dev`. Vite config proxies `/events` → `:3141`.

---

## Port Handling

Default port: `3141`. If in use:
- Server auto-increments to find a free port (3141, 3142, 3143…)
- Prints the actual port on startup: `claude-live listening on http://localhost:3142`
- The hook URL in the README uses `:3141` — users running on a different port must update their hook config. This is called out in the README.

## Setup Instructions (README)

1. `npx claude-live` — starts the server and opens the browser
2. Add to `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse":   [{ "matcher": "", "hooks": [{ "type": "command", "command": "echo \"$CLAUDE_HOOK_DATA\" | curl -s -X POST http://localhost:3141/hook -H 'Content-Type: application/json' -d @- || true" }] }],
    "PostToolUse":  [{ "matcher": "", "hooks": [{ "type": "command", "command": "echo \"$CLAUDE_HOOK_DATA\" | curl -s -X POST http://localhost:3141/hook -H 'Content-Type: application/json' -d @- || true" }] }],
    "Stop":         [{ "matcher": "", "hooks": [{ "type": "command", "command": "echo \"$CLAUDE_HOOK_DATA\" | curl -s -X POST http://localhost:3141/hook -H 'Content-Type: application/json' -d @- || true" }] }],
    "Notification": [{ "matcher": "", "hooks": [{ "type": "command", "command": "echo \"$CLAUDE_HOOK_DATA\" | curl -s -X POST http://localhost:3141/hook -H 'Content-Type: application/json' -d @- || true" }] }]
  }
}
```

3. Start a Claude Code session — the graph comes alive

## Out of Scope (v1)

- Persistent history / replay beyond the in-memory 100-event SSE buffer
- Remote/shared sessions
- Terminal-only (TUI) mode
- Authentication
- Settings UI within the app
- More than 6 simultaneous sessions
